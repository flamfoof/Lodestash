# Lodestash v2 Rewrite — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking. Per the owner's global CLAUDE.md §6, tasks state the
> interfaces, the tests that prove them and the done criteria; they do not script every line.
> Phases P5–P8 get their own detailed plan, written against the code as it stands after P4.

**Goal:** Restructure Lodestash into an app whose engine is the single owner of the catalog,
serving one derived `/v1` API to its own web UI and to a standalone thin-client MCP server, with
the UI held to the design by a measured contract.

**Architecture:** [v2 architecture spec](../specs/2026-11-16-v2-architecture-design.md). Keep
`lodestash-core`/`-ingest`/`-ai`; add `lodestash-protocol` (operation catalog) and
`lodestash-engine` (absorbs `lodestash-app` and the desktop writer/read model); reduce
`lodestash-api` to an adapter and `lodestash-desktop` to a window; rebuild the UI in `web/`.

**Tech stack:** Rust 1.96 stable (std file locks available), rusqlite 0.32 (bundled SQLite),
axum 0.8, rmcp 2.2, schemars 1, Tauri 2.11, Svelte 5, Vite 6, Playwright (Chromium), Bun.

## Global constraints

- Work on branch `rewrite/v2`. Commit per task; **never push**; never commit to `main`.
- Commit messages end with the session's `Co-Authored-By` trailer; append `[skip ci]`.
- Code follows the spec; a divergence updates the spec (or the owning doc) in the same commit
  (repo CLAUDE.md rule 2). New dependencies get a line in `docs/TECH-STACK.md` (rule 5).
- Invariants (repo CLAUDE.md): local-first, non-destructive, MCP↔REST 1:1 for agent operations,
  status lifecycle `discovered → indexed → identified → confirmed`, the seven-value `media_type`
  enum, `/v1` versioning, product name Lodestash, crates `lodestash-*`.
- Existing catalogs must keep opening. Migrations are additive and preceded by a backup.
- Tests never touch the user's catalog or config: use `tempfile` and `LODESTASH_CATALOG` /
  `LODESTASH_CONFIG_DIR`. A test that hangs past 5 s fails unless it declares a longer budget.
- Gates per task: `cargo test --workspace`, `cargo clippy --workspace --tests -- -D warnings`,
  `cargo fmt --all --check`; doc-touching tasks also `node scripts/check-docs.mjs`.

### Task R.3: Identity follows content (review finding, deferred from R.2)

`reconcile_moves` keeps a moved file's identity only when its new path is one no row holds. Two
ordinary workflows still strand hand tags: renaming files so one takes another's name in the same
scan (the row at that path keeps its tags but now holds different bytes), and a cross-volume move
seen by the watcher as copy-then-delete (the copy is inserted as a new, untagged row before the
original vanishes). Design to settle in `DATA-MODEL.md` §6 first: match displaced rows to open
paths by content hash as one permutation, and merge a vanished row into a fresh duplicate that
carries no user data; never guess between equal candidates (the same-name tie-break in
`pair_moves` guesses today).

- [x] `DATA-MODEL.md` §6 states the rule and its ambiguity cases
- [x] Tests: a three-way rename rotation keeps each row's tags with its bytes; copy-then-delete
  across two rescans keeps the tagged identity; two equal candidates are left unmatched
- [x] Commit `fix(core): identity follows content through renames onto held paths and copy-then-delete`

*As built (2026-11-18):* the defect was real — seven of the eleven scenarios below failed against
the old matching. The rule is `DATA-MODEL.md` §6.1 and the decisions behind it
[ADR-0025](../../decisions/ADR-0025-identity-follows-content.md); the code is
`crates/lodestash-core/src/catalog/moves.rs` (`Catalog::reconcile_moves`, which now answers a
`Reconciled`), and `record_crawl` lets a read hash decide over the size-and-mtime gate.

- **Where the design guidance was changed, and why.**
  - *An overwritten row moves to its match only when another row's bytes arrive on its path.*
    The guidance moved it whenever its old bytes turned up at an open path — which hands the tags
    to the backup when a file is copied aside and then edited, on every save. With no arrival the
    row stays, as it did before.
  - *A file moved over another* (`mv -f`) is not in the guidance: two rows want one path. The
    arriving row takes it (its bytes are there); the old row, whose bytes are nowhere, is
    **superseded** — kept, missing, under `.lodestash-superseded/<asset id>/`.
  - *Take-over needs something to carry.* A vanished row with no user data absorbs nothing, so
    deleting one of two untouched duplicates changes no ids.
  - *The pairing rule uses the longest shared path suffix* (unique on both sides), not only the
    file name, so a folder tree moved whole keeps its same-named duplicates apart without
    guessing. Leftovers of equal count are no longer paired in sort order.
- **Hashing.** The matching never needs a hash the crawl skipped: a row brings its recorded
  hash, a path is open only if its file was read, and a duplicate is judged by its recorded
  hash. The second scan of a copy-then-delete reads no file at all, so `reconcile_moves` no
  longer returns early when no record carries a hash.
- **Tests** drive `persist::rescan_source` — the function the watcher's rescan now calls — over
  real files, and read back through a `CatalogReader`
  (`crates/lodestash-engine/src/tests_identity.rs`): a swap, a three-way rotation, a rename onto
  a held path with the old file kept, copy-then-delete across two rescans (tags, favourite,
  collection, import record, embedding, full-text search and undo all follow), a copy kept
  beside its original, two equal candidates (and their resolution once one is left), a
  duplicate with user data, trashed and in-pack rows, a file moved over another, a file copied
  aside and edited, and the property test (random renames, swaps, rotations and overwrites; 24
  cases in the suite, 800 run once by hand). The pairing rule, each of the fourteen kinds of
  user data, unreadable history and the gate are in `catalog/tests_moves.rs`.
- **Not closed:** two files of the same size and mtime that exchange names pass the gate at both
  paths (§6.1 "Limits"); moves between sources are not matched.
