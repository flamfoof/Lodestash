# v2 P3 — The API as an Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or
> superpowers:executing-plans. Tasks state interfaces, tests and done criteria (owner's global
> CLAUDE.md §6); they do not script every line.

**Goal:** `lodestash-api` becomes a thin adapter over the engine: routes derived from the
operation catalog, two kinds of caller, a change feed, byte routes, and the first slice of UI
operations — enough for the web UI's Library screen to run on real data.

**Architecture:** [v2 spec](../specs/2026-11-16-v2-architecture-design.md) §5–§6, §8;
[ADR-0021](../../decisions/ADR-0021-engine-owns-the-catalog-ui-is-a-web-client.md),
[ADR-0024](../../decisions/ADR-0024-the-boundary-fails-closed.md). Parent plan:
[`2026-11-16-v2-rewrite.md`](2026-11-16-v2-rewrite.md) (its global constraints apply; this file
replaces its two-task P3 outline). What the UI needs: the "Outcome" section of
[`2026-11-17-v2-p7-library.md`](2026-11-17-v2-p7-library.md).

**Tech stack:** axum 0.8, tokio, `lodestash-protocol` (operations macro, schemars), the engine.

**Order:** 3.1 → 3.2 → 3.3 are sequential (same files). 3.4 and 3.5 can follow in either order.
3.6 closes the phase.

### Task 3.1: The engine implements `Operations`; the router is derived

**Files:** `crates/lodestash-engine/src/ops/*.rs` (new: one module per area), the domain half of
`crates/lodestash-api/src/{lib.rs,export.rs,discovery.rs,jobs.rs}` moves into the engine;
`crates/lodestash-api/src/routes.rs` shrinks to the derived router.

- The import queue and leases, approvals, the export sandbox and copy, discovery cursors and the
  heavy-slot limiter move from `ServerState` into the engine. `ServerState` keeps only what an
  HTTP adapter owns (tokens, sessions, the allow-list view).
- `impl lodestash_protocol::Operations for Engine` — every agent and engine-audience operation,
  each returning `Result<Out, ApiError>` built from `EngineError`/`CoreError::kind()`.
- The router is generated from `OPERATIONS`: path parameters + query (GET/DELETE) or + JSON body
  (POST/PUT) assembled generically and decoded with the operation's input type; handlers run on
  the blocking pool. The query decoder uses the input schema to tell a one-element list from a
  scalar.
- The allow-list gate is keyed by operation name from the catalog (no second list).
- Mutating agent operations still pass the approval gate exactly as `ENGINE-API.md` §8.4 says.
- [ ] Every existing `lodestash-api` route test passes against the derived router (shapes, statuses)
- [ ] The MCP end-to-end tests (`crates/lodestash-mcp/tests/e2e.rs`) pass unchanged
- [ ] A catalog operation with no engine implementation does not compile
- [ ] `routes.rs` has no per-operation handler left; `cargo tree -p lodestash-api` shows no rusqlite
- [ ] Commit `refactor(api): routes are derived from the operation catalog`

### Task 3.2: Two callers — the UI session and request checks

**Files:** `crates/lodestash-api/src/{auth.rs,session.rs}` (new), router layers.

- Agent: `Authorization: Bearer <handshake token>` → `Caller::Agent`. UI: `GET /session?code=`
  exchanges a one-time code (60 s, single use, minted in-process by `ServerState::mint_ui_code`)
  for an `HttpOnly; SameSite=Strict; Path=/` cookie → `Caller::Ui`, then redirects to `/`.
- `Audience::Ui` operations refuse a bearer caller (`403 denied`); the UI may call agent
  operations and is not subject to the agent allow-list or approval gate.
- `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (else `421`); any `Origin` header must be
  same-origin; a cookie-authenticated non-GET without a matching `Origin` is refused (`403`).
- [ ] Tests: wrong `Host` → 421; cross-origin POST with the cookie → 403; a bearer caller on a `Ui`
  operation → 403; a reused or expired code → 401; no credentials → 401 with the envelope;
  the cookie never appears in a response body or log line
- [ ] Commit `feat(api): the UI is a second kind of caller, with its own session`

### Task 3.3: Status, the change feed, the generation header

- `GET /v1/status` → `EngineStatus` plus `config_recovered` / `config_unreadable` (UI and agent).
- `GET /v1/events` (SSE): `changed {catalog_gen, jobs_gen, config_gen, origins[]}` from the
  engine's change bus, `status` on engine status change, a comment heartbeat every 15 s; a slow
  consumer is dropped, never buffered without bound.
- Every JSON read response carries `X-Lodestash-Gen: <catalog generation it reflects>`.
- [ ] Tests: a write produces one `changed` event with a higher generation; the header on a read
  after a write is ≥ the event's generation; a client that stops reading is disconnected
- [ ] Commit `feat(api): status, a change feed, and the generation every read reflects`

### Task 3.4: Bytes

- `GET /v1/assets/{id}/thumb|preview|mesh|slottex/{slot}|file`: async, streamed, single-range
  `Range` (a request without `Range` answers 200 with the whole body — fixes review U11),
  `ETag` from the content stamp with `If-None-Match` → 304. Media generation is the engine's
  (`media.rs`); the desktop's `lodestash://` handler is not extended.
- Agent callers pass the egress / byte-release gate; the UI caller does not.
- [ ] Tests: `Range: bytes=0-9` → 206, 10 bytes, correct `Content-Range`; no `Range` on a 20 MiB
  file → 200 with the full length; `If-None-Match` → 304; an agent without byte release → the
  documented refusal; an in-pack asset streams from its archive without extraction
- [ ] Commit `feat(api): thumbnails, previews, meshes and files are /v1 routes`

### Task 3.5: The app serves its UI, and can run without a window

**Files:** `crates/lodestash-api/src/static_ui.rs`, `crates/lodestash-desktop/src/lib.rs` (flags).

- The built `web/dist` is embedded in release builds and read from disk in debug; the server sets
  the CSP (no inline script, no remote sources); unknown non-`/v1` GETs fall back to `index.html`.
- `lodestash-desktop --serve` starts engine + server with **no window**, prints one line
  `http://127.0.0.1:<port>/session?code=<code>` to stdout, and exits on Ctrl-C or when stdin
  closes. `--background` is `--serve` without the printed code, exiting after 30 idle minutes.
  Both write the handshake with `exe` set. `LODESTASH_ENGINE_JSON` and `LODESTASH_CONFIG_DIR`
  override the handshake path and config directory (tests, the web gate).
- A new dependency for embedding (e.g. `rust-embed` or `include_dir`) gets its TECH-STACK line.
- [ ] Test (spawned process, temp dirs): `--serve` prints a URL that, followed, returns the UI's
  `index.html` with a session cookie; `/v1/status` answers Ready; closing stdin ends the process
- [ ] The MCP launch test passes against the real binary with `--background`
- [ ] Commit `feat(desktop): --serve and --background run the engine and its UI without a window`

### Task 3.6: UI operations, first slice — what the Library screen needs

**Files:** `crates/lodestash-protocol/src/{ops.rs,dto/*.rs}`, engine `ops/`, schema export,
`web/src/api/generated.ts` (generated).

Typed outputs replace `serde_json::Value` for these (wire-compatible additions to `ENGINE-API.md`
§3, documented there in the same commit):

- **`AssetSummary`** gains `size_bytes`, `stats`, `favorite`, `imported_in` (+ changed-since flag),
  tags as `{namespace, value, source, confidence}`, and `package.publisher`.
- **`AssetDetail`**: dependency edges `{asset_id?, name, kind, source, state, same_pack,
  declared_path}`, collection membership, effective licence, library name, per-type `stats`.
- **Operations (audience `Ui` unless noted):** `query_assets` (filters: text + mode, media types,
  statuses, libraries, tags, tri and size buckets, favourites, trash; sort; cursor paging; `total`),
  `library_counts` (status / library / type facets and the nav badges), `set_favorite`,
  `trash_assets`, `restore_assets`, `tag_assets` / `untag_assets` (as the person),
  `collection_add` / `collection_remove`, `ignore_link` / `restore_link`, `recent_ops`, `undo` /
  `redo` (by op id), `get_settings` / `update_settings` (the `Settings` DTO), `list_traits`,
  `reveal_asset`, `open_asset`, `pick_folder`. Every write returns `{op_id?, changed, gen}`.
- `query_assets` is served by the engine's read model (the snapshot; its sort and filter semantics
  and tests are the contract).
- `protocol.schema.json` is exported by a test/bin; `scripts/gen-api-types.mjs` turns it into
  `web/src/api/generated.ts`; both have `--check` and run in `bun run web:check`.
- [ ] Tests: each operation through HTTP as a UI caller on a temp catalog, results read back by a
  separate call; a bearer caller is refused on each `Ui` operation; `query_assets` paging returns
  every asset exactly once under a concurrent write; undo by op id reverts that op and not a newer
  agent op
- [ ] Commit `feat(api): the Library's operations — query, counts, writes that name their op`
